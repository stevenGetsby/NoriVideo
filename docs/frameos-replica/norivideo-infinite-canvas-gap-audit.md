# NoriVideo 无限画布对 FrameOS 差距审计（独立复核）

审计日期：2026-07-18  
审计范围：入口、画布管理、节点与连线、生成与派生处理、素材与工作流、保存与恢复、权限、3D 导演台、视觉与验证边界  
FrameOS 基线：`docs/frameos-replica/frameos-canvas-bundle-evidence.md` 记录的本地 App 运行时与 bundle 只读证据  
NoriVideo 基线：当前工作区源码与本轮不接外部服务的定向自动化回归

## 1. 结论

### 1.1 画布入口不是缺失项

当前源码已经有真实可达的无限画布入口，不是占位按钮：

- 全局展开和折叠导航进入 `/canvas`。
- 全局 Hub 支持“作品 → 项目 → 画布”，并支持 `/canvas/:projectId/:canvasId` 深链。
- 项目工作台支持 `/workflow/:projectId/workbench-premium2/canvas/:canvasId`。
- 项目侧栏、项目 Header、项目卡片和项目卡菜单均有入口。
- `CanvasWorkspace` 支持画布创建、切换、重命名和删除；只读账号不会显示写入口。

关键实现：

- `src/components/frameos/FosShell.tsx`
- `src/components/frameos/FosCanvasHubClient.tsx`
- `src/components/frameos/FosProjectHeader.tsx`
- `src/components/frameos/works/FosWorkPanels.tsx`
- `src/app/[locale]/canvas/[[...segments]]/page.tsx`
- `src/features/canvas/CanvasWorkspace.tsx`

### 1.2 不能据此宣称“所有能力已经 1:1 验收”

在现有 FrameOS 证据能够定义的功能范围内，本轮没有发现一个“FrameOS 已证实存在、而 NoriVideo 源码完全没有对应实现”的高置信静态功能缺口。节点、连线、分组、布局、剪贴板、素材、工作流、生成器、派生处理、任务恢复、离线草稿、revision 冲突和 3D 导演台均能追踪到真实前端状态、API、数据库或 worker。

但是，以下四类仍没有完成端到端验收，因此准确结论是“代码层高覆盖”，不是“像素级及运行时全量 1:1 已完成”：

1. 未消费真实图片、视频、音频、TTS 或 3D 服务额度。
2. 未在真实触控板和系统剪贴板授权环境逐项验证手势、媒体粘贴与 Electron/浏览器事件冲突。
3. 为保护 FrameOS 云端数据，FrameOS 的创建、保存、上传、生成、重命名和删除写链没有被执行。
4. 未在同尺寸窗口中完成 FrameOS 与 NoriVideo 的逐页截图叠图或像素差比较。

## 2. 状态定义

| 状态 | 含义 |
| --- | --- |
| 已实现 | 源码存在完整可达链，且本轮自动化至少覆盖其关键契约 |
| 静态闭环，E2E 未验 | 前端、API、任务或持久化链完整，但仍依赖真实设备、外部服务或人工交互 |
| Nori 增强 | NoriVideo 超出当前 FrameOS 证据，不应误判为复刻缺口 |
| 行为差异 | 两边均有能力，但冲突、失败或快捷键策略不完全相同 |
| 明确验收缺口 | 当前无法用既有证据支持“已经 1:1”的部分 |

`静态闭环，E2E 未验` 不等于入口不存在，也不等于外部服务一定可用。

## 8. 权限与范围隔离

画布 GET 使用项目读取授权；创建、修改、删除、document、ops、模板写入、任务提交/取消/重试和 3D 文档 PUT 使用 `storyboardWrite`。API 还会同时验证 projectId、canvasId、nodeId 或 taskId 的范围归属，不能只靠前端隐藏按钮。

当前权限映射中，管理员和分镜师可写无限画布；编剧和资产师可读。只读态关闭节点拖拽、连线、生成、上传、画布管理和 3D 场景修改，但保留预览、下载、历史和 3D 查看。

本轮已通过跨项目 Canvas scope、旧写路由拒绝、只读 UI 与写权限专项测试。没有使用真实多账号会话做浏览器级串号测试，因此最终上线前仍应做一次 admin、storyboard、writer、asset 四角色黑盒验收。

## 9. 视觉对齐结论

已经能确认的公共视觉 token：

- 画布背景 `#0d0d0d`。
- 普通节点背景 `#1c1c1c`。
- 主交互蓝 `#3b82f6`。
- 普通节点圆角 10px。
- 右键菜单和落空菜单为 160px 级宽度。

但这些 token 相同不等于像素级 1:1。NoriVideo 仍没有完成以下视觉验收：

- FrameOS 与 NoriVideo 同窗口尺寸的全画布截图叠图。
- 工具栏、生成器、菜单、历史弹窗、素材面板和 3D 导演台逐状态截图差分。
- 100%、125%、150% 系统缩放和窄窗口响应式检查。
- 不同媒体宽高比、超长标题、中文/英文和错误文案的溢出检查。

`ProductionNode.tsx` 使用浅色内联视觉，与暗色普通节点不同；该节点是 NoriVideo 的生产数据投影增强，不是当前 FrameOS 原生节点复刻门槛。若希望整张 NoriVideo 画布视觉统一，仍应单独重做其暗色样式，但不能把它计为 FrameOS 功能缺失。

因此，“功能 token 已对齐”可以成立；“已经像素级 1:1”目前不能成立。这是本审计唯一明确的 1:1 验收缺口，而不是一个已知静态业务功能缺口。

## 12. 上线前关键阻断点

### P0：阻止“1:1 已验收”声明

1. 用真实生产构建和真实账号逐一点击所有入口，确认没有旧构建或缓存提供历史前端。
2. 对 FrameOS 和 NoriVideo 做同尺寸、同缩放、同节点数据的逐状态截图差分。

4. 在真实系统剪贴板权限下验证文本、图片、视频、音频和 GLB 粘贴。
5. 分别消费一次文本、普通图片、蒙版改图、视频、TTS、音乐、音效和 3D provider，并核对任务、计费、素材和节点终态。

### P1：稳定性验收

1. 用真实 MySQL/Redis/worker 制造刷新、断网、重连、取消、重试和 worker 重启。
2. 两个标签页并发编辑普通画布和同一 3D 文档，检查 409、服务端版本和浅合并结果。
3. 使用大图、长视频、大 GLB、100 文件批量上传和 200 个 3D 对象做性能与内存测试。
4. 用 admin、storyboard、writer、asset 四类账号做浏览器级权限和资产隔离回归。

## 13. 最终判断

- “现在有画布入口吗？”——有，且入口和深链是实际实现。
- “核心无限画布子功能是否已在代码层覆盖？”——在当前 FrameOS 证据范围内，高置信覆盖，没有发现明确静态漏项。
- “能否确认所有子功能已经 1:1？”——不能。外部服务、真实设备、FrameOS 写链和像素差仍未验收。
- “下一步最值得做什么？”——先做生产构建双端截图差分与真实输入设备验收，再按最小付费样本跑完整生成矩阵；不要继续凭静态按钮数量判断完成度。
