# FrameOS「我的任务」原生 App 取证

取证日期：2026-07-17  
页面：`https://www.frameos.cn/#/my-assignments`  
取证方式：本地 FrameOS App 运行时只读观察，并对当前 App bundle 中的页面分支和 API client 做交叉核对  
原则：未分配、提交、通过、驳回、完成、恢复或批量修改任何 FrameOS 云端任务

## 1. 证据边界与结论

FrameOS 的「我的任务」不是生成队列页面，而是面向人工协作的跨项目任务中心。当前版本已确认包含作品、项目和任务类型筛选，按处理阶段组织的标签页，任务表格，任务详情抽屉，以及按状态和权限出现的分配、提交、审核、完成和恢复操作。

本文区分两类证据：

| 状态 | 含义 |
| --- | --- |
| 运行时已验证 | 当前 App 页面中实际渲染或可只读打开，并记录了布局、文案或条件分支 |
| Bundle/API 中存在 | 当前 App bundle 中存在明确的调用链；为避免改变云端数据，本次没有发送对应写请求 |

因此，本文可以作为 NoriVideo 复刻信息架构、状态词和 API 边界的原版基线，但不能据此声称所有状态转换都已经在 FrameOS 云端做过端到端写入验证。

## 2. 页面结构

### 2.1 筛选区

页面顶部提供三个筛选维度：

- 作品。
- 项目。
- 任务类型。

任务类型的当前选项为：

- 资产设定。
- 分镜设计。
- 视频制作。

作品与项目是级联业务范围，任务类型对应生产阶段。当前证据没有显示自由文本搜索、执行人筛选、日期区间或优先级筛选，因此这些能力不能作为 FrameOS 已验证功能写入 1:1 验收项。

### 2.2 标签页

普通执行视角下确认三个标签：

1. 待我处理。
2. 审核中。
3. 已完成。

账号具备审核权限时，页面会增加「待我审核」。这是权限条件分支，不应让所有账号固定显示一个无权操作的审核标签。

### 2.3 表格

任务列表表头依次覆盖：

| 列 | 展示内容 |
| --- | --- |
| 任务 | 阶段、项目/分集语义组成的任务标识 |
| 状态 | 当前人工协作状态 |
| 负责人 | 当前执行人；未分配状态可为空 |
| 相关时间 | 随任务阶段展示分配、提交、完成或更新时间 |
| 操作备注 | 当前审核/操作备注摘要 |
| 操作 | 当前账号在该状态下允许执行的动作和详情入口 |

列表按每页 10 条分页。当前只读取证确认了分页容量与分页控件，不宣称已验证超大数据量、末页回退或并发更新后的页码校正行为。

## 3. 任务详情抽屉

「查看详情」从右侧打开约 `420px` 宽的抽屉。已确认字段包括：

- 阶段。
- 执行人。
- 项目。
- 分集。
- 分配时间。
- 提交时间。
- 完成时间。
- 更新时间。
- 操作备注。

抽屉保留列表上下文，而不是跳转到一张独立详情页。当前运行时证据没有确认评论流、附件区、机器生成日志或完整事件时间线，不能仅因后端存在任务状态变更就推断这些 UI 已经存在。

## 4. 状态与动作

### 4.1 状态词

当前 App 使用以下五种面向用户的状态：

| 状态 | 业务含义 |
| --- | --- |
| 待分配 | 尚未指定负责人 |
| 进行中 | 已分配，等待执行人处理 |
| 待审核 | 执行人已提交，等待审核 |
| 已完成 | 已通过审核或被有权限的账号标记完成 |
| 已驳回 | 审核未通过，等待修改后重新提交或恢复处理 |

标签页和状态不是一一同义：例如「待我处理」是当前用户视角的集合，而「进行中」是任务本身的状态。NoriVideo 不应把标签名直接存成数据库状态。

### 4.2 动作词

当前 UI 分支与 API client 共同确认以下动作：

- 分配。
- 重新分配。
- 提交。
- 重新提交。
- 标记完成。
- 通过。
- 驳回。
- 恢复进行中。
- 查看详情。

动作会随任务状态、当前账号是执行人还是审核人、以及权限变化，不是每行恒定展示全部按钮。本次没有触发写操作，因此不记录未经验证的成功提示、失败提示、二次确认文案或服务端副作用。

其中「重新提交」和「恢复进行中」是独立语义：前者将驳回后的交付再次送审，后者把任务重新置回执行阶段。复刻时不应把两者都简化为普通「提交」。

## 5. 原版 API 基线

当前 App 使用的任务接口前缀为：

```text
/api/creative/projects/collaboration/assignments
```

### 5.1 读取接口

| 方法与路径 | 用途 |
| --- | --- |
| `GET /my` | 当前用户的执行任务列表 |
| `GET /pending-review` | 当前用户有权审核的任务列表 |
| `GET /pending-review-count` | 待审核数量，用于标签/徽标 |
| `GET /list` | 项目或管理视角的任务列表 |
| `GET /candidates` | 当前任务可选负责人 |

### 5.2 写接口

| 方法与路径 | 用途 |
| --- | --- |
| `POST /assign` | 分配或重新分配单个任务 |
| `POST /submit` | 提交或重新提交任务 |
| `POST /approve` | 审核通过 |
| `POST /reject` | 驳回并记录备注 |
| `POST /mark-complete` | 有权限的账号直接标记完成 |
| `POST /reopen` | 将任务恢复为进行中 |
| `POST /batch-assign` | 批量分配 |
| `POST /batch-approve` | 批量通过 |
| `POST /batch-reject` | 批量驳回 |

以上写接口为当前 bundle 的明确调用边界；本次遵循只读原则，没有向 FrameOS 云端发送这些请求。批量 API 的存在也不能单独证明当前「我的任务」页面在所有账号和所有标签下都显示批量操作控件。

## 6. 对 NoriVideo 复刻的约束

1. 「我的任务」应以人工任务/assignment 为主数据，不能直接拿 BullMQ 或模型生成任务代替。
2. 作品、项目、任务类型筛选，以及标签页计数必须使用同一套权限和过滤口径。
3. 「待我审核」只能对有审核权限的账号出现。
4. 服务端应返回或可靠派生当前账号可执行的动作，前端不应只靠角色字符串猜测。
5. 驳回后的执行人需要有「重新提交」闭环；已完成任务需由有权限账号执行「恢复进行中」。
6. 详情抽屉需要保留阶段、执行人、项目、分集、四类时间和备注字段。
7. 默认分页容量应对齐每页 10 条；若 NoriVideo 增加游标分页或无限滚动，应标注为产品增强而非原版 1:1 行为。
8. 批量写接口、状态按钮和详情只读展示必须分别验权，不能因为用户能读取任务就允许提交或审核。

## 7. 尚未验证的状态

- 每个动作的确认弹窗、成功 toast 与服务端错误文案。
- 批量选择控件在不同标签和权限账号下的完整显示规则。
- 无任务、网络失败、加载重试与超长字段截断的全部视觉状态。
- 筛选条件是否写入 URL、刷新后是否保留，以及多页筛选后的页码校正规则。
- 执行人被停用、项目/分集被删除、两人同时审核时的冲突处理。
- 是否存在任务附件、评论、操作事件时间线或任务级机器生成进度。

这些项目需要新的只读证据或在隔离测试账号/测试数据上验证；在此之前不得推断补全为 FrameOS 原生能力。

当前准确结论：NoriVideo 已具备可用的人工协作闭环，核心状态与权限问题已修复；距离页面动作 1:1 的明确差距，是把分配、重新分配和恢复进行中按原版条件放回“我的任务”行内/详情操作区。事件时间线、项目级批量分配和 canonical API 属于增强能力。
